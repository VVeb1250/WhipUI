# Co-design the missing decision

1. **Ground the job.** Read the real request, project and existing evidence. For
   unclear problem/audience/outcome, load Intent `strategize/REFERENCE.md`; for
   missing user evidence, load `investigate/REFERENCE.md` and its relevant research
   reference. Identify what must be learned and choose a feasible method. Ask the
   owner about product facts they know. Their taste is not evidence of target-user
   behavior. Research output without participants/data remains a plan/hypothesis.
   Game requests enter [game.md](game.md) for player decisions and play context;
   reuse that result instead of starting a second product interview.

2. **Make the task work.** For flow/state uncertainty load Intent `journey`; for
   grouping/navigation use `organize`; for structured screens use `wireframe`;
   for microcopy/content use `articulate`. The wireframe viewer is optional: use
   it when a multi-screen board needs slide controls, otherwise a compact HTML
   wireframe or native diagram is sufficient. A design prototype may simulate
   consequential recovery with clearly synthetic state, without production APIs.
   Do not embed an entire viewer or forbid simulation solely because upstream
   mandates that format. Read only the relevant references and
   specify the main path plus consequential failure/recovery states. Show a flow
   or minimal clickable artifact when it resolves uncertainty. Do not design every
   state of a speculative product. Completion is an understandable task sequence
   with known constraints, not a large document or an AI-generated persona.

3. **Make taste concrete when it matters.** For a new/unresolved visual world,
   use Impeccable's mode/world/first-viewport method through SOURCE-MAP. Ground it
   in the task, real assets and supplied references, then make a representative
   viewable prototype early. In guided work, receive feedback on the visible
   composition and experience before building the whole speculative product;
   record accepted/rejected traits, not a generic style label. Offer a materially
   different alternative only when it answers the unresolved choice. Explicit
   one-shot/delegation proceeds autonomously with reversible, provisional choices.
   Existing identity and precise matches use Garden preservation and skip new-world
   discovery. A named generic/weak composition can receive one compact Taste or
   frontend-design challenge; neither is an automatic second pipeline or aesthetic
   veto over approved choices. Familiar patterns, craft and subject identity are
   assessed separately. A functional-only question skips this visual branch.

4. **Set the success condition.** Use Intent `measure` for an unresolved outcome
   or measurement question, `evaluate`/`include` for relevant UX/accessibility
   risks. Distinguish artifact checks, owner preference and actual task testing.
   Agree what the next artifact/experiment should answer. No universal aesthetic
   score or fixed sample count certifies success; match method and evidence to the
   claim. Keep important open assumptions visible.

5. **Return an implementable decision.** Use Intent `specify` only when a separate
   handoff needs it. Otherwise update the existing brief with facts/constraints,
   confirmed decisions (source), delegated choices, proposals, critical states and
   relevant checks. Three to five bullets suffice for a settled small task. Reuse
   PRODUCT/DESIGN/surface records; do not create a parallel state system. A design-only
   request ends with the requested concept/flow/prototype. An authorized build
   continues directly to build.md using the same decisions.
